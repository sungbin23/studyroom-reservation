# Chapter 05 맥락질의 인터뷰 워크북 — 도서관 스터디룸 모바일 예약 시스템

## 1. 실습 대상
| 항목 | 작성란 |
|---|---|
| **선택한 장소·과업** | 전공 강의실 앞 복도 / 도서관 모바일 웹에서 다음 주 수요일 오후 2시에 4명이 쓸 스터디룸 예약하기 |
| **참여자 포함 기준·가명** | 도서관 스터디룸을 한 달에 1회 이상 예약하는 3학년 학생 (가명: P01) |
| **조사 목표** | 모바일 화면(Time-grid)에서 빈 시간을 찾고 선택할 때 발생하는 실제 조작 패턴과 오류 원인 파악 |
| **관찰 시작·종료 조건** | 도서관 웹사이트 접속 시 시작 / 예약 완료 화면 도달(또는 포기) 시 종료 |
| **촬영·녹음 여부와 동의** | 얼굴 및 개인정보 화면 제외, 화면을 터치하는 손 모양만 녹화 동의 구함 |
| **중단 조건** | 참여자가 학번/비밀번호를 입력할 때 녹화를 잠시 멈추거나 시선을 돌림 |

## 2. 시작 안내
> "오늘은 사용자를 평가하는 것이 아니라 서비스와 작업 과정을 이해하려고 합니다. 쉬는 시간에 이동하면서 급하게 예약하신다고 상상하고, 평소 하시던 속도대로 편하게 폰을 만져주세요. 제가 중간중간 왜 그렇게 누르셨는지 짧게 여쭤보겠습니다. 원하지 않는 질문에는 답하지 않거나 언제든 중단할 수 있습니다."

## 3. 관찰 초점
| 초점 | 찾은 내용 1 | 찾은 내용 2 |
|---|---|---|
| **행동 순서** | 화면 접속 후, 가로 모드로 폰을 눕힘 | 날짜 선택 후 스크롤을 무작위로 위아래로 움직임 |
| **사용하는 도구·정보** | 모바일 웹 브라우저 (사파리/크롬) | 단체 톡방의 회의 시간 투표 결과 확인 |
| **중단·방해** | 복도에서 지나가는 동기를 마주쳐 잠시 멈춤 | 표의 칸이 너무 작아 잘못 누르고 뒤로가기 버튼을 찾음 |
| **우회 방법** | 원하는 시간(14시)이 꽉 차 있자, 다른 방이 아닌 30분 뒤(14시 30분) 빈칸을 찾음 | 빈 방이 없자 에브리타임 앱을 켜서 빈 강의실 위치를 검색함 |
| **오류·복구** | 14시 칸 대신 14시 30분 칸을 오터치함 | 화면 하단으로 한참 내려가서 '취소'를 누르고 다시 스크롤함 |

## 4. 시간순 관찰 기록 (가상 시나리오)
| 시간 | 관찰 사실·행동 | 사용자 발화 | 연구자 추론 | 사용자 확인 결과 |
|---|---|---|---|---|
| **00:30** | 폰을 가로로 돌린 후 화면을 핀치 투 줌(확대) 함 | "글씨가 너무 작아서 세로로는 아예 안 보여요." | 세로 모드 최적화가 안 되어 있어 시각 정보 파악 불가 | 모바일 예약 시 항상 가로로 돌린다고 확인함 |
| **01:15** | 화면을 위아래로 빠르게 반복해서 스와이프함 | "4명이 들어가는 방이 어디 있는지 방 번호를 못 외워서요." | 방 수용 인원 정보가 표와 직관적으로 연결되지 않음 | 방 크기(인원) 정보를 찾느라 스크롤을 반복함 |
| **02:40** | 14:00 칸을 터치하려다 14:30 칸을 누름 | "아, 또 잘못 눌렀네. 칸이 너무 다닥다닥 붙어 있어요." | 손가락 터치 영역보다 표의 셀 크기가 작아 오터치 유발 | 평소에도 1~2번은 꼭 잘못 누른다고 답함 |
| **03:10** | '뒤로 가기'를 눌러 첫 화면으로 튕김 | "아... 처음부터 다시 해야 하네." | 예약 취소(돌아가기) 버튼의 가시성 부족 | 웹 자체 뒤로가기를 누르면 날짜 세팅이 다 날아간다고 함 |

## 5. 해석 확인
| 회차 | 중립적 확인 문장 | 참여자의 답 | 수정된 해석 |
|---:|---|---|---|
| **1** | "제가 보기에는 방금 글씨가 작아서 화면을 가로로 돌리신 것 같은데 맞나요?" | "네, 세로로 보면 표가 다 잘려서 시간대가 안 보여요." | (해석 유지) 모바일 가로형 표는 한 화면에 들어오지 않아 강제 가로 모드를 유발함 |
| **2** | "아까 위아래로 계속 스와이프 하신 건 4인용 방을 찾으려고 그러신 건가요?" | "네, 근데 방 번호만 있고 몇 인용인지 안 써 있어서 방마다 다 눌러봐야 해요." | (해석 수정) 단순히 정보를 찾는 것뿐만 아니라, 시스템이 인원수 정보를 직관적으로 주지 않아 불필요한 '탐색 터치'가 강제됨 |
| **3** | "원하는 시간이 꽉 찼을 때, 다른 방을 안 찾고 30분 뒤 시간을 누르신 이유가 있나요?" | "방 위치를 바꾸면 팀원들이 헷갈려 해서, 차라리 시간을 조금 미루는 게 편해요." | (해석 추가) 사용자는 장소(방) 변경보다 시간 변경을 덜 부담스러워함 (우선순위 파악) |

## 6. 핵심 사건
| 사건 ID | 관찰 근거 | 사용자 결과 | 왜 중요한가? | 남은 질문 |
|---|---|---|---|---|
| **C01** | 화면 확대 및 잦은 가로/세로 모드 전환 | 시각적 피로도 증가, 탐색 시간 지연 | 모바일 뷰 비최적화가 근본적인 사용성 저하의 원인임 | 굳이 표(Grid) 형태를 고집해야만 하는가? |
| **C02** | 인원수를 확인하기 위해 방 번호를 일일이 터치해 봄 | 불필요한 반복 조작 유발, 데이터 낭비 | 사용자가 원하는 핵심 조건(인원수) 필터링이 불가능함 | 시작할 때 인원수를 먼저 고르게 하면 어떨까? |
| **C03** | 좁은 칸 오터치 후 브라우저 '뒤로 가기'를 눌러 초기화됨 | 과업 강제 종료, 극심한 짜증 유발 | 오터치가 쉬운 구조와 복구 불가능성이 최악의 경험을 만듦 | 한 번 선택한 조건을 유지한 채 방만 바꿀 수는 없을까? |

## 7. 인사이트와 설계 기회
| 인사이트 | 연결 근거 ID | 반복 행동·원인·필요 | 설계 의미 |
|---|---|---|---|
| **I01** | C01, C02 | 학생들은 전체 예약 현황표를 보는 것보다, 자신에게 필요한 특정 조건(4인용)을 먼저 찾고 싶어 한다. | 모바일 화면에서는 모든 정보를 늘어놓는 Grid 방식이 부적합하며, 조건 기반 필터링이 필수적이다. |
| **I02** | C03 | 좁은 터치 영역으로 인한 오작동이 빈번하며, 이를 복구하는 과정(취소/뒤로가기)이 직관적이지 않다. | 손가락으로 누르기 쉬운 큰 터치 영역(List/Button)과 명확한 '수정' 버튼 배치가 필요하다. |

| 설계 기회 | 관련 인사이트 | 기대 행동 변화 | 검증할 질문 |
|---|---|---|---|
| **O01** | I01 | 첫 화면에서 표 대신 `인원수`와 `시간`을 먼저 입력받는 필터링 UI 제공 | 화면 확대나 무작위 스와이프 없이 즉시 원하는 조건의 방 목록을 확인하게 됨 | 리스트만 보여주었을 때, 다른 시간대 현황을 보지 못해 답답해하지는 않을까? |
| **O02** | I02 | 좁은 칸 대신 큼직한 `카드형 리스트 버튼`과 직관적인 `취소/수정 버튼` 제공 | 오터치 발생률이 현저히 줄어들고, 실수하더라도 처음부터 다시 할 필요가 없음 | 카드형 리스트가 기존 시간표보다 예약 완료 속도를 실제로 단축시키는가? |
