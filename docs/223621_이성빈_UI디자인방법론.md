# Chapter 02 UI 디자인 방법론 워크북 — 도서관 스터디룸 모바일 예약 시스템

## 1. 분석 대상과 대표 과업
- **선택한 캠퍼스 서비스**: 대학 도서관 그룹 스터디룸 모바일 예약 시스템
- **주요 사용자 한 유형**: 조별 과제 모임 장소를 급하게 찾아 예약해야 하는 3학년 재학생
- **사용 장소·시간**: 전공 수업이 끝난 직후 쉬는 시간 (약 10분 내외), 학생들이 몰려나오는 시끄러운 복도를 걸어가며
- **함께 사용하는 기기·도구**: 좁은 화면의 스마트폰 (전공 서적을 한 손에 들고 있어 주로 한 손으로 화면을 조작함)
- **가장 불편한 대표 과업**: 원하는 날짜에 4명이 들어갈 수 있는 스터디룸의 '빈 시간대'를 찾아 예약하기
- **실패했을 때의 결과**: 빈 방을 제때 찾지 못하거나 예약을 실수해서 팀원들의 일정이 꼬이게 됨. 결국 학교 밖의 비싼 유료 스터디 카페를 사비로 예약해야 함.

## 2. 관찰 근거

| 근거 ID | 구분 | 내용 | 출처·상황 | 신뢰도·한계 |
|---|---|---|---|---|
| **E01** | 행동 | 스마트폰 화면에 꽉 찬 가로형 예약 시간표(Time-grid)를 한눈에 보지 못해 좌우로 계속 스와이프하다가 엉뚱한 시간대를 잘못 터치함. | 수업 직후 복도에서 모바일로 예약하는 학생 3명 관찰 | 참여자 소수의 한 장면이며, 기종에 따라 불편 정도가 다를 수 있음 |
| **E02** | 발화 | "아, 도대체 지금 몇 시부터 몇 시가 비어있는 거야? 색깔 구분이 잘 안 가네." | 조별 과제 팀장이 단체 대화방에 예약 화면 캡처본과 함께 남긴 불만 | 사용자의 일시적인 짜증 섞인 과장이 포함되어 있을 수 있음 |
| **E03** | 자료 | 모바일 예약 화면이 최적화되지 않고, PC 버전과 동일한 넓은 엑셀 표 형태의 UI가 그대로 축소되어 제공됨. | 현재 대학 도서관 모바일 웹사이트 예약 현황판 캡처 | 디자인 문제 외에도 서버 지연 등이 예약 실패에 영향을 줬을 수 있음 |

## 3. 문제문장

> `조별 과제를 위해 스터디룸을 찾는 학생`은 `이동 중인 짧은 쉬는 시간`에 `빈 스터디룸을 빠르고 정확하게 예약`하려 하지만, `모바일 화면에 최적화되지 않은 복잡한 가로형 표(Time-grid) 구조와 불명확한 시각적 피드백` 때문에 `엉뚱한 시간을 잘못 터치하거나 빈 방을 찾지 못해 예약을 포기하는 결과`를 경험한다.

## 4. 방법론 선택

| 방법론 | 판단 |
|---|---|
| **HCD (Human-Centered Design)** | 실제 학생들의 '이동 중 한 손 모바일 사용'이라는 맥락을 분석하고 UI를 개선하는 핵심 방법론으로 활용. |
| **디자인 씽킹** | 표를 없애고 검색 방식을 바꾸는 등 초기 아이디어 발산에 활용하되, 구체적인 화면 검증에는 한계가 있어 초기 단계에만 씀. |
| **Lean UX** | '시간표 대신 조건 필터링 리스트를 주면 완료 시간이 단축될 것'이라는 가설을 세우고, 종이 프로토타입으로 빠르게 검증할 때 차용. |

- **선택한 접근과 이유**: **Lean UX를 결합한 HCD 중심 접근**. 모바일 사용 맥락과 조작 불편(E01, E02)이라는 명확한 관찰 근거가 있으므로 HCD를 바탕으로 문제를 정의하고, 가설을 세워 Lean UX 방식으로 빠르게 핵심 과업(예약) 프로토타입을 검증하는 것이 가장 효율적이다.

## 5. 핵심 아이디어 3프레임

| 프레임 | 사용자 행동 | 시스템 반응 | 가정 |
|---:|---|---|---|
| **1. 시작** | 첫 화면에서 `인원수`와 `사용 시간`을 큰 버튼으로 누름 | 선택한 조건에 딱 맞는 '현재 비어있는 스터디룸' 목록만 필터링하여 세로 리스트로 보여줌 | 사용자는 전체 예약 현황을 탐색하는 것보다, 내 조건에 맞는 결과만 보는 방식을 더 선호할 것이다. |
| **2. 핵심 행동** | 추천된 리스트 최상단의 방 `예약하기` 버튼을 누름 | 최종 확인을 위해 방 번호와 시간을 화면 중앙에 팝업으로 띄움 | 목록과 큰 버튼을 제공하면, 표에서 발생하던 스와이프 오터치가 사라질 것이다. |
| **3. 완료·피드백** | 팝업에서 `확인`을 누름 | 예약 완료 메시지와 출입용 `QR코드`를 크게 보여줌 | 시각적으로 명확한 QR코드를 주면 사용자가 예약 성공을 확신할 것이다. |

## 6. 검증 계획

> **검증 가설**: 복잡한 시간표 대신 '조건 입력 및 리스트 필터링' UI를 제공하면, 이동 중인 사용자의 스터디룸 예약 완료 시간이 가상 기준 2분에서 30초 이하로 줄어들 것이다.

| 항목 | 작성란 |
|---|---|
| **가장 위험한 가정** | 시스템 추천 리스트를 못 미더워하고, 굳이 '전체 시간표'를 보고 남들의 예약 현황을 확인하고 싶어 할 수도 있다. |
| **프로토타입 범위** | 모바일 화면 크기의 종이 프로토타입 3장 (조건 입력 ➔ 추천 리스트 ➔ 완료 QR코드) |
| **지표 1** | 예약 완료 시간 (초 단위 측정) / 목표값: 30초 이하 (가상) |
| **지표 2** | 조작 중 오터치 및 취소 횟수 / 목표값: 0회 (가상) |

## 7. 개인 비판 검토

| 질문 | 답변 |
|---|---|
| **근거 없이 내가 추정한 것은 무엇인가?** | 학생들이 무조건 '자신이 원하는 조건의 방 하나'만 빠르게 추천받기를 원할 것이라 추정했다. 실제로는 다른 방들의 예약 현황을 보며 유동적으로 시간을 조정하고 싶어 하는 학생도 있을 수 있다. |
| **이 해결안이 소외할 수 있는 사용자는 누구인가?** | 모임 시간이 확정되지 않아 여러 시간대를 동시에 비교하며 예약해야 하는 사용자에게는 필터링 방식이 오히려 답답할 수 있다. |
| **기술보다 정책·정보 품질 문제는 없는가?** | 화면을 아무리 고쳐도, 실제로는 비어있는데 '노쇼(No-show)' 패널티 관리가 안 되어 시스템상으로는 '예약 꽉 참'으로 뜨는 정책 및 동기화 문제가 더 클 수 있다. |
| **반대 해결안 하나와 장점은 무엇인가?** | 아예 화면 UI를 없애고 '카카오톡 챗봇'을 도입하는 방안. "오늘 2시 4명"이라고 텍스트만 치면 예약되므로, 이동 중 접근성이 압도적으로 좋다. |

## 8. AI 사용 기록

- **사용 AI**: Gemini (생성형 AI)
- **사용 목적**: E01~E03 근거를 바탕으로 한 문제문장 도출, 3프레임 핵심 UI 구조 기획, 디자인 방법론 논리성 검토
- **주요 프롬프트**: "도서관 스터디룸 예약에 관한 관찰 근거를 바탕으로 해결책이 배제된 문제문장을 만들어 줘", "가로형 표(Time-grid)를 대체할 직관적인 3프레임 스케치를 제안해 줘"
- **채택하지 않은 내용**: 학생의 모든 시간표와 동선을 GPS로 자동 추적하여 빈 방을 추천한다는 제안 (과도한 개인정보 수집 우려로 거부함)
- **직접 확인·수정한 내용**: AI가 제시한 복잡한 AI 추천 로직 대신, 사용자가 직접 인원/시간을 입력하는 '단순 조건 필터링' 방식으로 기획의 방향을 현실적으로 수정함.
